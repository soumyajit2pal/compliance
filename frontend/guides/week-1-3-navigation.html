Week 1–3 portal navigation and workflow guide

Week 1–3 reference for the local UAT portal at https://localhost:8010/. The Help description reflects the 20 November 2026 update. Records, counts, tasks and permissions come from the live API.

Find your way around

Use Compliance at a glance for Home and My tasks for assignments and decisions. Expand Regulations for the Regulatory library, Notification families and Clauses / Para. Expand Administration for the settings your role permits. Groups with no permitted screens are omitted.

The header shows the current location, workspace search, Help, Notifications, your identity and Sign out. The footer provides Need a hand?, My role and Other applications. On a phone, use Open navigation and Close navigation; the surrounding backdrop also closes the menu.

Search works only within available areas. A user can search notifications, tasks or help; an Admin can search people and settings. The source search includes the official reference number. The keyboard shortcut is Command/Ctrl + K. It opens search without changing permissions.

Reading the portal

The current interface uses charcoal text and headings, plum actions and selection accents, white panels and a soft neutral page background. The palette is shared by login, navigation, filters, tables, source details, clause trees and administration. Body text remains 16px; form values are 14–16px, with 16px on phones. Compact labels/help and shared panel spacing reduce clutter while preserving readable text and touch targets. Status badges retain green, amber and red with explicit words. Keyboard focus uses a visible plum outline.

These display changes preserve navigation, imports, role scopes and approval controls. Shared theme, compact-layout and searchable-control styles follow the retained prototype styles. Your identity remains in the account controls; scope restrictions and admin access notices remain visible.

Sign in and first-login windows

Use https://localhost:8010 on this computer. The local TLS certificate is self-signed, so accept its browser warning or have the public certificate trusted locally. The normal portal no longer listens on HTTP. Sign in normally; the browser protects the sign-in request automatically. A secure-sign-in error stays in the form so you can refresh or retry without an unencrypted submission. If it persists, contact the portal administrator.

  • Welcome back: the compact white sign-in form uses plum actions and retains the original bank wordmark. Desktop shows the introduction alongside it; phones show the brand header and form. Enter your Standard username/portal password or LDAP username/directory password. Show password / Hide password changes field visibility. User guide opens this guide without signing in. The Sign-in help disclosure has been removed from login. SSO remains excluded.
  • Loading: a progress bar and status show when pages or actions are waiting. Form buttons and dependent dropdowns show busy states while their work runs. Progress also appears inside dialogs. Longer waits show Still working; errors stop loading and keep the relevant error message visible. Downloads use the browser’s download progress.
  • Demo user: UAT only. While Loading demo users appears, you can still enter username/password and sign in manually. A failed list offers Retry; a deployment without demo access hides the chooser. Once loaded, search by name or username, then select an account. Active Standard demo accounts with effective roles remain listed before and after first login, including after a password change. Selection fills the username and, when it still matches a known public demo password, the password. Otherwise enter the account’s current password; private passwords are never disclosed or reset. Choose Sign in to continue. First sign-in still requires setting a personal password. Inactive, LDAP and role-less accounts are excluded. Prod cannot enable this selector.
  • Set your own password: a new Standard account must change its temporary password before workspace navigation opens. Use 12–72 UTF-8 bytes with upper/lowercase letters, a number and a symbol. Demo selection does not bypass this gate.
  • Demo LDAP: when enabled in UAT, enter a new username beginning with the documented prefix (currently bmock, for example bmock01) and the configured demo LDAP password. Its synthetic department code is DEMO-001, separate from Home organisation. Confirm your work profile; an administrator approves the LDAP department and assigns roles/scope separately. Sign in again after approval. Prod refuses demo LDAP.
  • Confirm your work profile: check the work email prefilled from LDAP or enter it manually, then select Home organisation. The Admin review and role assignment follow profile confirmation.
  • Your LDAP department code has changed: application access is blocked. Compare previously approved code with current LDAP details, enter an optional explanation and choose Request department update. Check request status displays decisions; Sign out and sign in again refreshes LDAP. Home organisation and roles remain separate. Missing or ambiguous values cannot be submitted as a replacement.
  • Your access request is pending: an administrator must assign approved roles and scopes. Use Check access again after the assignment.

Searchable dropdowns

Click a dropdown and type a name, code or part of the label to filter its available choices. Use the arrow keys and Enter, or click a result. Escape closes the results and restores the selected value; a second Escape can close the surrounding filter panel or dialog. Tab leaves the current choice unchanged. Clear the search to browse available choices. A no-match message means refine the search; typing cannot create a new value. Required fields and disabled choices still apply. Source edition, parent-clause and role-scope choices retain their existing limits.

This same control is used in login, filters, registration, clauses, editions and administration. Checkbox lists and date fields keep their existing controls. Older browsers without Popover support keep native dropdowns. In the Regulatory library, More filters still has X and Close; Apply filters applies the choices and closes the panel.

Understand domain setup: Draft only and Ready for review

A regulatory domain is the subject area covered by a notification, such as KYC / AML / CFT. Compliance Department is the default owner. New domains start as Draft only. The setup status controls whether a Draft can be submitted for Compliance review.

Status shownWhat it meansWhat you can do
Draft only · Owner department not assignedThe bank-approved owning department has not been recordedChoose the domain, complete the form and save a Draft. Ask an Admin to complete the domain setup before submitting for review
Draft only · Review submissions not enabledAn owner is recorded, but review submissions have not been enabledSave and prepare the Draft. Ask an Admin to enable review submissions after the bank has approved the setup
Ready for review · Domain setup completeAn owning department is recorded and review submissions are enabledComplete the source, Clauses / Para and independent reviewer/approver assignments, then submit. This status does not approve the notification

The domain selector shows Draft only or Ready for review beside each name. Selecting a domain displays the reason and the next step. The same status appears in Master data and the source record; the Workflow tab explains the limit for a Draft. Submit for Compliance review stays disabled while the domain is Draft only. Draft editing remains available, and the API independently enforces the submission restriction.

An authorised Admin uses Administration → Master data → Regulatory domains → Set owner, selects the bank-approved owning department and checks Allow submissions for Compliance review when appropriate. Leaving it unchecked keeps the domain available for Drafts only. Authors cannot activate domains through registration; choosing a department is not itself bank approval. The underlying activation flag and existing submission checks are unchanged.

Understand Clause / Para

A Clause / Para is one numbered part of a regulatory notification. Para means paragraph. Use the numbering and original wording from the source. For example, a source may say Clause 14.2 or Para 5; both are captured in Instrument workspace → Clauses / Para → Add clause / para. The bank’s explanation stays in Bank’s internal interpretation. A parent clause / para groups sub-parts within the same source edition.

  1. In the Draft edition you created, select the parent in the tree and choose Add child clause.
  2. Enter the Item label. The Source clause / para number preview below it shows the full number that will be saved. Under parent 4(1), either (iii) or iii previews 4(1)(iii). Under parent 5.1, enter .1 to preview 5.1.1. Under an unnumbered heading, enter the full printed label such as 4.
  3. Enter the Clause heading and Original regulatory text. The portal fills Source page reference from the selected branch and the item number. You can edit the reference or add a PDF page number. The portal keeps your edits as you change the item label. Choose Use hierarchy to generate the reference again. Bank interpretation and clause requirements opens expanded. Choose Save as Draft to open the saved child under the selected parent.

Use Add clause to create the first clause or start a new branch. Under Clause placement, select Use source hierarchy or Enter manually. The default hierarchy option creates missing ancestor headings and fills Source page reference, for example Chapter I - Preliminary › C. Definitions › 4(1)(i). To save a lead-in such as 4(1), enter Paragraph 4 and Subparagraph (1) with Item blank. A lead-in with original wording receives a permanent clause code. For manual placement, enter the printed Source clause / para number, choose a Parent clause if applicable and type the Source page reference. The form keeps your entries for each option while it is open and saves only the selected placement. You can edit a saved page reference, parent or numbering in Edit Draft clause.

The tree shows navigation headings by title and source clauses by their printed number and title. Open a source clause to see its permanent clause code in the details. New navigation headings use their internal IDs for parent links. Existing heading codes are retained for reference lookup and audit history.

Select a clause in your Draft to find its actions above the wording. Add child clause is the filled button, Edit Draft clause has a pencil and an outline, and Link earlier clause appears as an underlined action when available.

Open Clauses / Para → Workspace to see source clauses across the instruments and editions you can access. Enter a reference, heading or wording in Search clauses. Expand Search options to choose a search type or clause approval status. Words or reference finds keywords and reference prefixes. Phrase finds consecutive words. Reference only searches codes and numbers. For Exact wording, first choose one specific source edition. Use the numbered pages and Per page control above or below the results in Workspace and Register.

Choose an Instrument by title or reference to explore its hierarchy. Browsing starts with the current approved edition. Choose a Draft, historical or future edition when needed. Use the arrow beside a heading or clause to expand or collapse it. Opening a clause shows its path and nearby clauses automatically. Choose Show more clauses to continue through a longer branch.

Open a clause to see its edition’s hierarchy on the left and its original wording, bank interpretation and source information on the right. On desktop, drag the divider between these panes to adjust the explorer’s width, or focus it and use the arrow keys. Your browser remembers the width in both the Clause workspace and the instrument’s Clauses tab. On narrow screens, expand Instrument & clause hierarchy above the text when needed. Back to results restores the search and page you came from. Links and reload open the same clause and edition, even outside the first batch.

Example: register and approve a new RBI notification

  1. Home → Register a notification, or Regulatory library → New instrument.
  2. Basic information: enter the official title, reference number when issued, short title and issue/effective dates. The official reference is the regulator's identifier; the portal creates a separate permanent instrument code in the INS-{regulator}-{domain}-{instrument type}-{issue year}-{sequence} format, using the selected master codes (for example, INS-RBI-REG-KYC-ACT-2026-001). The issue year comes from Issue date. Clauses extend the full instrument code with -C001; obligations extend the full primary-clause code with -OBL-001. Codes remain permanent across later metadata edits and obligation revisions. Legacy codes remain available as retained aliases; see the root README's shared identifier conventions.
  3. Classification: select regulator, regulatory domain, instrument type, materiality and confidentiality. Read the domain setup message: Draft-only domains can be saved, but need Admin setup before review submission. Keywords make the record easier to find.
  4. Accountability: choose the accountable department and an eligible interpretation owner. The owner list is checked for the chosen organisation.
  5. In Source & version, attach the authoritative file using a format permitted by the [document upload policy](../../README.md#document-uploads-and-size-limits--24-november-2026). Creating the Draft uploads the file and creates the first source version.
  6. Review & create: inspect the summary. Previous step keeps entered values and the selected file. Choose Create Draft instrument. Leaving the wizard discards unsaved browser entries.
  7. Open Clauses / Para and choose Add clause for a new branch or Add child clause after selecting a saved parent. Enter the original wording and page reference. Record the bank's interpretation separately. The portal assigns the permanent clause reference on save.
  8. Maker → Workflow → Next step. Resolve the listed blockers, then choose Submit for Compliance review. Select the eligible reviewer and a different final approver. Send to Compliance reviewer puts the edition in the reviewer’s My decisions queue.
  9. Reviewer → My decisions → Open Compliance review. Read the source and Clauses / Para, then choose Record Compliance review. Add a rationale and confirm independence. Return for correction, rejection and eligible delegation are available under Other workflow actions.
  10. Approver → My decisions → Open final approval. This task appears after independent review. Read the source and clauses, choose Approve source edition, add a rationale and confirm independence. Maker, reviewer and approver must be different people.
  11. An approved effective edition becomes Current. A future-effective approval is preserved and can become current only when eligible. History retains source versions, status changes, assignments, decisions and audit events.

Example: revised edition or amendment source

Open an approved Instrument workspace → New version. Enter the new version number/date and effective date, identify the approved edition it supersedes, attach the new source and explain the changes. Capture its Clauses / Para and obtain a new independent review and approval. The previous approved edition and its source remain available in Versions and History.

The library manages source editions within one continuing instrument. Notification families now connects separately issued originals and amendments while retaining their own source editions and implementation. Obligation creation, delivery and assurance transactions remain separate wider workflows. A revised source edition never asserts implementation or assurance completion.

Keep parents within the selected edition

  1. In a Draft you created, select a parent in the tree and use Add child clause. For example, select 5 and enter .1 to add 5.1. Open 5.1 and enter .1 to add 5.1.1.
  2. In Edit Draft clause, the Parent clause picker shows eligible parents in that source edition and excludes the selected clause and its descendants. Choose Top-level clause to place a clause at the root.

Link an earlier clause

  1. An eligible Author selects a clause in the Clause workspace or instrument's Clauses tab and chooses Link earlier clause.
  2. Select an approved earlier clause from the notification family, choose the reference type and effective date, and explain the basis. Linking retains each clause's own source and does not copy it or change its parent.
  3. Choose different named Reviewer and Approver recipients and submit. Both must be authorised to inspect the cited sources.
  4. The named Reviewer records review through My decisions or Notification families → Review and approval history. Final approval opens only for the named independent Approver after review. History retains both decisions and the cited clauses.
  5. Broader relationship lists/panels are hidden; this focused link and its approval workflow remain available.

Work with Notification families

  1. Open Regulations → Notification families. Unlinked existing notifications appear as standalone families; prototype example records are not installed.
  2. An Author chooses Register amendment for a separate source record or Link existing notification. Select independent named Reviewer and Approver recipients. Family membership begins after approval; it never transfers implementation or obligation links.
  3. Choose As of date, optionally enter a title or reference in Search notifications, and select Apply filters. The date applies to approved source history and regulatory deadlines; delivery details use the latest retained records. Open a family and select a notification row to inspect its Source editions (the default), retained Business implementation or Regulatory deadline history. Future amendments remain Upcoming, and historical/future positions are read-only.
  4. Manual business-scope registration is deferred: there is no Add participating department action or separate registration shortcut on the source record. The source retains one lead regulatory department. The Business implementation tab appears only for actual retained registrations, with narrow read access, confidentiality checks and named owners preserved. Empty implementation links open Source editions; empty development notices are hidden. Obligation ownership and applicability will be captured separately in the later obligation workflow.
  5. For an already registered scope, its named Business Owner can still choose Assess implementation, identifies the exact effective approved source and submits Completed or No impact. Completed needs every source-specific action completed with accepted independent evidence; No impact requires no delivery actions. Independent review and approval are required. Source, action or evidence changes require reassessment.
  6. An Author proposes source-cited regulatory deadlines for independent approval. Original, current and next dates remain in history. Descendants inherit the nearest effective ancestor date until their own approved override applies; internal action extensions do not change it.
  7. Open each notification’s library record to inspect its source. Obligation tabs, links and counters are hidden for this release; old obligation-tab links open Source editions. Totals cover only authorised sources and business scopes. Empty implementation sections, totals and approval-history tables are hidden. Review and approval history appears when proposals exist. Implementation is never a compliance-assurance conclusion.

Import existing regulatory records

Use this workspace to bring existing regulatory registers into the portal in bulk. For example, an existing Excel list can be profiled, corrected, independently validated and loaded as Drafts. A single new notification can be registered through Regulatory library → New instrument.

  1. Choose Download Excel template. Fill Regulatory records and optionally Clauses, starting at row 2. Read How to fill and the illustrative Example; Choices supplies current readable masters. Only the two data sheets are imported. A blank template creates no records.
  2. Give each linked record an Import reference, such as REG-001. Enter the usual instrument details and an exact Source file name, for example kyc-direction.pdf. Attach that file with the workbook. Alternatively, use the Source document ID from an earlier Upload source document; choose one source method per new record. The source's department and confidentiality must match the record.
  3. Each Clauses row uses the matching Import reference, one passage of Original regulatory text, a PDF page or document locator in Source page reference, and a separate Bank’s internal interpretation field. Choose one placement method per row. For automatic hierarchy, enter Chapter and any applicable Section, Paragraph, Subparagraph and Item in B–F. For 4(1)(i), enter 4, (1) and (i) as text. Every Item row needs its Subparagraph. Put the 4(1) lead-in on its own row with Item blank. Leave Parent clause reference and Source clause / para number blank. For explicit placement, leave B–F blank. Enter a unique Clause import reference, the printed Source clause / para number and the Parent clause reference when the row has a parent. The preview shows the resulting links.
  4. New records start as Draft edition 1.0. To add clauses to an existing maker-owned Draft, fill only Import reference, its Existing instrument code, the exact Source edition and optional Existing register reference in its Regulatory records row. Existing metadata and source are retained. To add under an existing navigation heading, enter its path using the automatic hierarchy columns. For explicit placement under an existing parent with original wording, copy its permanent clause code from the clause details. Approved/other-maker editions cannot be imported into. Earlier-clause links remain a separate approval flow.
  5. Choose one required Primary regulatory domain, which supplies the permanent instrument ID segment. Optional Additional affected domains accepts other exact names/codes separated by semicolons. Owner choices include usernames and are checked for the selected department. The eight choice lists refresh from Oracle on every download and the workbook records the refresh time in IST. A saved file has no live connection. Use Excel dates, DD/MM/YYYY or YYYY-MM-DD. All affected domains still need ownership setup before normal review submission.
  6. Choose Import records & clauses, select the workbook and its source files together, then Upload and profile. Limits are 10,000 total data rows across both sheets, 50 MiB expanded XLSX, 50 source files and 100 MiB total content. The Admin sets the [per-file limits](../../README.md#document-uploads-and-size-limits--24-november-2026). Keep the template sheet names. The portal also accepts CSV and older instrument-only templates and technical clause imports.
  7. Validation preview shows complete record/edition groups, proposed hierarchy, separate wording/interpretation, source downloads/hashes and sheet/row errors. Inspect sources before validating content. Search and the searchable record-type filter retain group context. A missing/cyclic/cross-edition parent, duplicate or invalid field keeps its whole group correction-required. The source file, original rows and lineage are retained. Field corrections require a corrected workbook/new batch; omit unchanged valid groups already reserved by another pending batch. No in-place staged-row edit or pending-batch supersede/withdraw screen is provided.
  8. A global Compliance Reviewer other than the uploader opens the batch from My tasks, My decisions or the import notification. Use Open sources and rows to compare the workbook with the authoritative source, including record references, clause wording and parent links. If anything differs, ask the uploader to correct the workbook. Once the eligible rows have been checked, select Validate reviewed content and confirm the batch. The uploading global Author receives the task and notification to Load ready rows as Drafts. Both handoffs queue email for delivery through the configured SMTP relay. If a ready group’s source or eligibility changes, the selected load rolls back. Refresh validation preview rechecks pending groups for independent validation. The portal retains loaded rows and checks existing targets again before adding clauses.
  9. Migration Ready indicates that validated rows can be loaded. The Validation preview names the uploading Author for Reviewers and displays Load ready rows as Drafts for the Author. When the ready rows include notification relationships, choose an independent Compliance Reviewer and Final Approver for the proposals, then select Load Drafts and submit proposals. Open each proposal from the loaded group. Assigned users can open it from My decisions. Open the linked source editions in the Regulatory Library to submit the separate Draft source approvals. The profile and report reconcile loaded and pending rows and link their targets. Attached files support manual source checks. Keep the exact regulatory wording within Excel’s 32,767-character cell limit.

For a new amendment included in the workbook, fill Parent notification, Relationship and Relationship effective date in its Regulatory records row. For example, enter RBC-BASE, Amends and 1 January 2027 on the RBC-AMEND-2 row. RBC-BASE is the original’s Import reference. If the original is already registered, use its permanent instrument code. Check this mapping in Validation preview during content review. Final approval adds the amendment to the family with the effective date from Excel.

Live implementation rules retained from the prototype

The shared shell, colours, font families, icons, panels, tables, wizard and dialogs derive from the prototype. Live controls use actual Oracle data. Design-only role switching and SSO simulation are replaced by real Standard/LDAP sign-in. Unsupported later-phase buttons, fake exports/trends and illustrative business counts are omitted. Product flows use the real required fields and API validation; no visual change relaxes approval independence, source retention or access control.

Administrator access requests

Open Administration → Users & access. Standard and LDAP accounts are separate; Action required combines pending LDAP approvals and missing/ineffective roles. The banner, navigation count and Home access card link to this queue. Refresh access status reloads the current server state.

In LDAP users, search for a person or filter by Access status and Employee profile. Select Details to see that person’s work profile, roles and scope, next step and approved and observed LDAP/API values. Use Review employee profile request for a pending decision, Employee profile history for prior decisions, or Manage profile & roles for access assignments.

A new LDAP user confirms email and Home organisation. The complete LDAP/API employee profile is queued automatically. Open Employee profile changes, review the separate LDAP and API fields, Home organisation and existing scope, then Approve or Reject with a reason. Approval establishes the complete employee snapshot and revokes sessions. The user must sign in again; if the API fails, this fresh sign-in can continue with the approved employee snapshot and a warning, provided LDAP is unchanged and no other restriction applies. Older requests are superseded if newer department details are observed. Rejected requests retain the reason; a new explanation is required to request reconsideration. Pending duplicate submissions return the same request.

Role assignment remains a separate Edit access action. Prepared roles do not bypass profile or department verification. Existing LDAP users complete the new full-profile approval setup. LDAP codes are compared only with approved LDAP values; API values only with their corresponding approved API fields. Leading zeroes remain intact. Historical department evidence is archived and does not fabricate full-profile approval. A return to the approved code closes a pending change as obsolete. Disabled accounts remain blocked. Department approval does not change Home organisation or roles/scopes. Standard password and access behavior are unchanged.

Access events create in-app notifications. Admin links open the affected account; each event displays its current status so a resolved request no longer appears to need approval. Read/unread notification state is separate from the current action queue. Saving roles revokes current sessions and the user signs in again.

Source edition selection and Draft changes

Open a record from the Regulatory library to read its current approved edition effective today. A pending edition remains available through Open pending edition or Source edition. A future-approved edition stays labelled Future effective and does not replace the effective reading default. If no approved edition exists, the portal shows the Draft with an explicit notice. My work, decision and edition-history links open their specific edition directly; switching tabs and reloading preserve that selection. Returning through the library restores the default.

The maker with Author access can select a Draft and use Edit draft version to correct its number, dates, predecessor, change summary, consolidated flag or source attachment. Leave the file blank to keep the source. Existing clauses and interpretation remain available; review them against any replacement source. Initial-Draft source/date edits also align the draft instrument, while subsequent-Draft edits leave the approved instrument unchanged.

Content is locked during review and after Compliance review. The maker may Withdraw to Draft, or the named reviewer/approver may Return for correction. Current review fields are cleared and the prior workflow remains in history. Edit the Draft and submit it again for fresh Compliance review and independent final approval. Approved source editions cannot be edited; use a new source edition for source changes or the separate approved-metadata correction flow for supported register fields.

Validation messages in dialogs

If a dialog submission fails, its error is shown at the top of the dialog and receives focus. Your entries stay in place so you can correct them and retry. A long dialog scrolls to the error. The message remains until the next attempt or a new dialog; it is not repeated in a toast behind the window. Success messages appear on the page after a successful dialog closes. If the session ends, the dialog closes and sign-in is shown.

For Add at least one source clause / para before submitting, cancel the review dialog, add clauses to the selected Draft edition, then submit again. The visibility fix does not remove this prerequisite.

One pending edition and Draft cancellation

Only one edition per instrument may be Draft, In review or Reviewed. While one is pending, Open pending edition replaces New version and a notice identifies the edition and required action. Complete approval, record a rejection, or cancel the Draft before creating another edition. Withdraw to Draft and Return for correction keep the pending slot occupied.

The maker with Author access can select Cancel draft and enter a reason of at least 10 characters. A Draft under review must first be withdrawn to Draft. Cancellation is permanent; the edition cannot be edited or submitted again. It remains in Source edition and Versions as Cancelled, with the reason, actor, date, source, clauses and prior workflow history retained. The approved effective edition stays unchanged. Use a different version number for a replacement edition.

Cancelling the initial Draft also closes the unapproved instrument as Withdrawn. Existing records are retained. If older data contains multiple pending editions, links identify them all; their makers must cancel extra Drafts before another submission can proceed. API checks enforce these rules even for stale browser tabs.

Add or edit master and organisation records

  1. As Admin, open Master data and choose a tab. In Other lookups, choose the lookup type and apply Search. Use Add for a new record or Edit beside an existing row.
  2. Enter its code, name and displayed attributes. A new code must be unique; existing codes are read-only. Reference dropdowns are searchable. New regulatory domains default to Compliance Department and start as Draft only. Enable review submissions once the domain is ready.
  3. Enter Reason for change, then save. A validation error stays in the dialog with your values. Cancel closes without saving. Inactive records remain retained for historical references.
  4. For organisations, open Organisation hierarchy, select a unit and choose Edit or Add child unit. Add child fills its parent; the page's Add organisation unit action starts a separate new unit. Select the type, parent and dates, record a reason and save. Parent options exclude the current unit and its descendants. A parent must be active and effective for a new link.
  5. Moving a unit recalculates descendant levels and changes the organisations included in descendant role scope. It does not move users' Home organisation, approve an LDAP department or change role assignments. Deactivate or move active children before deactivating their parent. The BANK root's structural settings stay protected.

Role display names can be edited; new permission roles and role code/activation changes require a deployment change. Regulators with retained non-Draft approval history cannot be overwritten by this editor. Master edits retain before/after audit evidence and the administrator's reason; this is not a business source approval.
