Week 1–3 portal navigation and workflow guide

Updated 30 October 2026. Applies to the local Oracle UAT portal at https://localhost:8010/. Navigation and forms follow the prototype structure, with the selected white-and-plum palette. Records, counts, tasks and permissions come from the live API.

Find your way around

The left navigation starts with Home, My work and My decisions. Expand Regulations for the Regulatory library, Notification families and Clauses / Paras. Expand Administration for permitted user, master, organisation, LDAP and Import existing regulatory records screens. Groups with no permitted screens are omitted. More tools and Release baseline have been removed from the sidebar, including the mobile drawer.

The header shows the current location, workspace search, Help, Notifications, your identity and Sign out. The footer provides Need a hand?, My role and Other applications. On a phone, use Open navigation and Close navigation; the surrounding backdrop also closes the menu.

Search works only within available areas. A user can search notifications, tasks or help; an Admin can search people and settings. The source search includes the official reference number. The keyboard shortcut is Command/Ctrl + K. It opens search without changing permissions.

Reading the portal

The current interface uses charcoal text and headings, plum actions and selection accents, white panels and a soft neutral page background. The palette is shared by login, navigation, filters, tables, source details, clause trees and administration. Body text remains 16px; form values are 14–16px, with 16px on phones. Compact labels/help and shared panel spacing reduce clutter while preserving readable text and touch targets. Status badges retain green, amber and red with explicit words. Keyboard focus uses a visible plum outline.

These display changes preserve navigation, imports, role scopes and approval controls. Shared theme, compact-layout and searchable-control styles follow the retained prototype styles. Your identity remains in the account controls; scope restrictions and admin access notices remain visible.

Sign in and first-login windows

Use https://localhost:8010 on this computer. The local TLS certificate is self-signed, so accept its browser warning or have the public certificate trusted locally. The normal portal no longer listens on HTTP. Sign in normally; the browser protects the sign-in request automatically. A secure-sign-in error stays in the form so you can refresh or retry without an unencrypted submission. If it persists, contact the portal administrator.

  • Welcome back: the compact white sign-in form uses plum actions and retains the original bank wordmark. Desktop shows the introduction alongside it; phones show the brand header and form. Enter your Standard username/portal password or LDAP username/directory password. Show password / Hide password changes field visibility. User guide opens this guide without signing in. The Sign-in help disclosure has been removed from login. SSO remains excluded.
  • Demo user: UAT only. Search by name or username, then select an account. Active Standard demo accounts with effective roles remain listed before and after first login, including after a password change. Selection fills the username and, when it still matches a known public demo password, the password. Otherwise enter the account’s current password; private passwords are never disclosed or reset. Choose Sign in to continue. First sign-in still requires setting a personal password. Inactive, LDAP and role-less accounts are excluded. Prod cannot enable this selector.
  • Set your own password: a new Standard account must change its temporary password before workspace navigation opens. Use 12–72 UTF-8 bytes with upper/lowercase letters, a number and a symbol. Demo selection does not bypass this gate.
  • Demo LDAP: when enabled in UAT, enter a new username beginning with the displayed prefix (currently bmock, for example bmock01) and the configured demo LDAP password. Its synthetic department is DEMO-001 — UAT mock department, separate from Home organisation. Confirm your work profile; an administrator approves the LDAP department and assigns roles/scope separately. Sign in again after approval. Prod refuses demo LDAP.
  • Confirm your work profile: new LDAP users confirm email and Home organisation. LDAP code/name are read-only directory details. Confirmation submits initial department verification; it does not approve the department or grant a role.
  • Your LDAP department code has changed: application access is blocked. Compare previously approved code/name with current LDAP details, enter an optional explanation and choose Request department update. Check request status displays decisions; Sign out and sign in again refreshes LDAP. Home organisation and roles remain separate. Missing or ambiguous values cannot be submitted as a replacement.
  • Your access request is pending: an administrator must assign approved roles and scopes. Use Check access again after the assignment.

Searchable dropdowns

Click a dropdown and type a name, code or part of the label to filter its available choices. Use the arrow keys and Enter, or click a result. Escape closes the results and restores the selected value; a second Escape can close the surrounding filter panel or dialog. Tab leaves the current choice unchanged. Clear the search to browse available choices. A no-match message means refine the search; typing cannot create a new value. Required fields and disabled choices still apply. Source edition, parent-clause and role-scope choices retain their existing limits.

This same control is used in login, filters, registration, clauses, editions and administration. Checkbox lists and date fields keep their existing controls. Older browsers without Popover support keep native dropdowns. In the Regulatory library, More filters still has X and Close; Apply filters applies the choices and closes the panel.

Understand domain setup: Draft only and Ready for review

A regulatory domain is the subject area covered by a notification, such as KYC / AML / CFT. Its setup status controls whether a Draft can be submitted for Compliance review.

Status shownWhat it meansWhat you can do
Draft only · Owner department not assignedThe bank-approved owning department has not been recordedChoose the domain, complete the form and save a Draft. Ask an Admin to complete the domain setup before submitting for review
Draft only · Review submissions not enabledAn owner is recorded, but review submissions have not been enabledSave and prepare the Draft. Ask an Admin to enable review submissions after the bank has approved the setup
Ready for review · Domain setup completeAn owning department is recorded and review submissions are enabledComplete the source, clauses / paras and independent reviewer/approver assignments, then submit. This status does not approve the notification

The domain selector shows Draft only or Ready for review beside each name. Selecting a domain displays the reason and the next step. The same status appears in Master data and the source record; the Workflow tab explains the limit for a Draft. Submit for Compliance review stays disabled while the domain is Draft only. Draft editing remains available, and the API independently enforces the submission restriction.

An authorised Admin uses Administration → Master data → Regulatory domains → Set owner, selects the bank-approved owning department and checks Allow submissions for Compliance review when appropriate. Leaving it unchecked keeps the domain available for Drafts only. Authors cannot activate domains through registration; choosing a department is not itself bank approval. The underlying activation flag and existing submission checks are unchanged.

Understand Clause / Para

A Clause / Para is one numbered part of a regulatory notification. Para means paragraph. Use the numbering and original wording from the source. For example, a source may say Clause 14.2 or Para 5; both are captured in Instrument workspace → Clauses / Paras → Add clause / para. The bank’s explanation stays in Bank’s internal interpretation. A parent clause / para groups sub-parts within the same source edition.

In Clauses / Paras → Workspace, All instruments / All editions is the default. The tree groups clauses by instrument and shows their recorded hierarchy, for example 5 → 5.1 → 5.1.1, with source numbers/headings above permanent portal references. Every clause shows its edition and source status. Repeated numbers from different editions remain separate; a parent and its children always belong to the same instrument and edition. Select the appropriate parent when capturing each clause.

Choose Current approved to read only approved editions effective today, across all instruments or one selected instrument. If none is effective for an instrument, no Draft/future/historical edition is substituted. Choose an instrument to list its specific editions, including editions with no captured clauses. An empty edition stays empty. The Instrument workspace's own Clauses tab keeps its separate edition selector and approved/effective default.

Opening a clause retains All/current/specific filters and shows the wording, interpretation, source document and permitted actions for that exact edition. Links and reload preserve the scope. Search and approval-status filters work within that scope; matching children retain their same-edition ancestors. Opening a parent context clears the text/status filters and retains the scope. Clear filters retains the instrument/edition choices. Changing instruments preserves All editions or Current approved; a specific edition resets to All editions for the new instrument. Selector changes clear the earlier clause/text/status selection. Register shares these filters and opens each exact clause without narrowing the browsing scope. Read edition/status badges when using Draft or historical material. On phones the selectors remain visible above the collapsible hierarchy.

Example: register and approve a new RBI notification

  1. Home → Register a notification, or Regulatory library → New instrument.
  2. Basic information: enter the official title, reference number when issued, short title and issue/effective dates. The official reference is the regulator's identifier; the portal creates a separate permanent instrument code in the INS-{regulator}-{domain}-{instrument type}-{sequence} format, using the selected master codes (for example, INS-RBI-REG-KYC-REGULATION-001).
  3. Classification: select regulator, regulatory domain, instrument type, materiality and confidentiality. Read the domain setup message: Draft-only domains can be saved, but need Admin setup before review submission. Keywords make the record easier to find.
  4. Accountability: choose the accountable department and an eligible interpretation owner. The owner list is checked for the chosen organisation.
  5. Source & version: attach the authoritative PDF, UTF-8 text or DOCX file, up to 20 MB. The first source version is created as version 1. The file is uploaded only when the completed Draft is created.
  6. Review & create: inspect the summary. Previous step keeps entered values and the selected file. Choose Create Draft instrument. Leaving the wizard discards unsaved browser entries.
  7. Instrument workspace → Clauses / Paras → Add clause / para: preserve the regulator's original wording. Enter the bank's interpretation separately, with heading, permanent clause / para reference, page reference and any same-version parent clause / para.
  8. Workflow → Submit for Compliance review: choose an eligible Reviewer and a different Approver. At least one source clause / para, the source document and a bank-approved active domain owner are required.
  9. Reviewer → My decisions → Open decision: inspect the source/clauses / paras and choose Record review. Add rationale and confirm independence. Return, reject and eligible delegation remain available for the assigned task.
  10. Approver → My decisions → Open decision: final approval opens after independent review. Add rationale, confirm independence and approve. Maker, reviewer and approver must be different people.
  11. An approved effective edition becomes Current. A future-effective approval is preserved and can become current only when eligible. History retains source versions, status changes, assignments, decisions and audit events.

Example: revised edition or amendment source

Open an approved Instrument workspace → New version. Enter the new version number/date and effective date, identify the approved edition it supersedes, attach the new source and explain the changes. Capture its clauses / paras and obtain a new independent review and approval. The previous approved edition and its source remain available in Versions and History.

The library manages source editions within one continuing instrument. Notification families now connects separately issued originals and amendments while retaining their own source editions and implementation. Obligation creation, delivery and assurance transactions remain separate wider workflows. A revised source edition never asserts implementation or assurance completion.

Keep parents within the selected edition

  1. Open the maker's Draft and choose Add clause / para, or edit a Draft clause.
  2. Parent clause offers only clauses in that source edition. Choose Top-level clause for a root; the edited clause and its descendants are excluded as parents.
  3. Save each recorded parent/child relationship to build 5 → 5.1 → 5.1.1. Changing editions refreshes the parent choices. Earlier-edition parent reuse is hidden in this release.

Link an earlier clause

  1. An eligible Author selects a clause in the Clause workspace or instrument's Clauses tab and chooses Link earlier clause.
  2. Select an approved earlier clause from the notification family, choose the reference type and effective date, and explain the basis. Linking retains each clause's own source and does not copy it or change its parent.
  3. Choose different named Reviewer and Approver recipients and submit. Both must be authorised to inspect the cited sources.
  4. The named Reviewer records review through My decisions or Notification families → Independent proposals and decisions. Final approval opens only for the named independent Approver after review. History retains both decisions and the cited clauses.
  5. Broader relationship lists/panels are hidden; this focused link and its approval workflow remain available.

Work with Notification families

  1. Open Regulations → Notification families. Unlinked existing notifications appear as standalone families; prototype example records are not installed.
  2. An Author chooses Register amendment for a separate source record or Link existing notification. Select independent named Reviewer and Approver recipients. Family membership begins after approval; it never transfers implementation or obligation links.
  3. Choose As of date, optionally enter a title or reference in Search notifications, and select Apply filters. The date applies to approved source history and regulatory deadlines; delivery details use the latest retained records. Open a family and select a notification row to inspect its Business implementation, Source editions or Regulatory deadline history. Future amendments remain Upcoming, and historical/future positions are read-only.
  4. An Author registers each business scope and its eligible Business Owner. Missing inherited scopes stay pending until registered. Effective roles covering that registered organisation gain narrow read access to the family, subject to source confidentiality; authoring authority is unchanged.
  5. The named Business Owner chooses Assess implementation, identifies the exact effective approved source and submits Completed or No impact. Completed needs every source-specific action completed with accepted independent evidence; No impact requires no delivery actions. Independent review and approval are required. Source, action or evidence changes require reassessment.
  6. An Author proposes source-cited regulatory deadlines for independent approval. Original, current and next dates remain in history. Descendants inherit the nearest effective ancestor date until their own approved override applies; internal action extensions do not change it.
  7. Open each notification’s library record to inspect its source. Obligation tabs, links and counters are hidden for this release; old obligation-tab links open Business implementation. Totals cover only authorised sources and business scopes. An empty population is Not assessed; implementation is never a compliance-assurance conclusion.

Import existing regulatory records

Use this workspace to bring existing regulatory registers into the portal in bulk. For example, an existing Excel list can be profiled, corrected, independently validated and loaded as Drafts. A single new notification can be registered through Regulatory library → New instrument.

  1. Administration → Import existing regulatory records → Upload source document preserves an authoritative source and shows its Source document ID. Copy that value for the matching record.
  2. Choose Download Excel template. Its Regulatory records sheet uses the registration screen's labels, such as Instrument title, Regulator, Primary regulatory domain, Additional affected domains, Regulatory owner department and Interpretation owner. Fill one actual notification per row, starting at row 2. Required fields and filling instructions appear in How to fill. Example contains one clearly labelled illustrative notification; Choices supplies current readable master values. Only Regulatory records is imported. The example, instructions and choices are excluded, and uploading a blank template creates no records.

All eight choice lists come from the current Oracle database on every download: regulator, primary domain, instrument type, materiality, confidentiality, department, eligible interpretation owners and additional affected domains. How to fill shows the download's refresh time in UTC. A saved Excel file is a snapshot; download a fresh template for updated choices. It contains no database password or live database connection. Draft-only domains remain available for Draft classification, while review submission requires setup for every affected domain.

  1. Enter one required Primary regulatory domain. It supplies the domain segment in the permanent instrument ID and stays distinct from Additional affected domains. For the optional additional field, enter each other domain's exact name or code from Choices, separated by semicolons; do not repeat the primary domain. These domains are saved as independent secondary assignments. Owner choices include the person's name and username; the person still needs Author access for the selected row's department. Exact portal names, existing master codes and owner usernames also work. An owner's full name must identify one active person; use the username when names repeat. Source document ID, owning department and confidentiality must match the uploaded source. Use Excel dates, DD/MM/YYYY or YYYY-MM-DD. The optional Short title and Applicability date fields are retained. Import checks the current database again; values that are no longer eligible need correction even if they appeared in an earlier download.
  2. Import source accepts UTF-8 CSV or XLSX, up to 20 MB/10,000 records. The original file, sheet, row and header labels are retained. The CSV template link provides the same screen headings without workbook formatting or example sheets. Older technical CSV headings remain accepted. Keep the Excel template's sheet names and place all actual rows in Regulatory records. To add more rows beyond the initial yellow entry area, continue in the same sheet beneath row 101; choice lists extend through row 10001.
  3. Source profile distinguishes correction-required, content-validation-pending, migration-ready and loaded rows. Inspect original rows and the exported profile report. Missing or ambiguous fields are reported with screen labels. Copying the illustrative example title into the records sheet is flagged for replacement with actual content.
  4. A different eligible Reviewer confirms independent content validation for eligible rows. An Author then loads ready rows as Drafts.
  5. Loading does not approve content. The normal source review/approval still applies; original source rows reconcile to loaded and pending populations.

Live implementation rules retained from the prototype

The shared shell, colours, font families, icons, panels, tables, wizard and dialogs derive from the prototype. Live controls use actual Oracle data. Design-only role switching and SSO simulation are replaced by real Standard/LDAP sign-in. Unsupported later-phase buttons, fake exports/trends and illustrative business counts are omitted. Product flows use the real required fields and API validation; no visual change relaxes approval independence, source retention or access control.

Administrator access requests

Open Administration → Users & access. Standard and LDAP accounts are separate; Action required combines pending LDAP approvals and missing/ineffective roles. The banner, navigation count and Home access card link to this queue. Refresh access status reloads the current server state.

A new LDAP user first confirms email and Home organisation once valid directory code/name details are available. Confirmation submits initial LDAP department verification. Open LDAP department changes, review the old/current code/name, Home organisation and explanation, select Approve or Reject and record a reason. Approval changes only the approved LDAP department and revokes sessions. The user must sign in again; the latest LDAP code must match. Older requests are superseded if newer department details are observed. Rejected requests retain the reason; a new explanation is required to request reconsideration. Pending duplicate submissions return the same request.

Role assignment remains a separate Edit access action. Prepared roles do not bypass profile or department verification. Existing LDAP users missing a baseline require administrator verification and fresh matching sign-in. Name-only changes refresh the name with history; codes are compared exactly, preserving leading zeroes and case. A return to the approved code closes a pending change as obsolete. Disabled accounts remain blocked. Department approval does not change Home organisation or roles/scopes. Standard password and access behavior are unchanged.

Access events create in-app notifications. Admin links open the affected account; each event displays its current status so a resolved request no longer appears to need approval. Read/unread notification state is separate from the current action queue. Saving roles revokes current sessions and the user signs in again.

Source edition selection and Draft changes

Open a record from the Regulatory library to read its current approved edition effective today. A pending edition remains available through Open pending edition or Source edition. A future-approved edition stays labelled Future effective and does not replace the effective reading default. If no approved edition exists, the portal shows the Draft with an explicit notice. My work, decision and edition-history links open their specific edition directly; switching tabs and reloading preserve that selection. Returning through the library restores the default.

The maker with Author access can select a Draft and use Edit draft version to correct its number, dates, predecessor, change summary, consolidated flag or source attachment. Leave the file blank to keep the source. Existing clauses and interpretation remain available; review them against any replacement source. Initial-Draft source/date edits also align the draft instrument, while subsequent-Draft edits leave the approved instrument unchanged.

Content is locked during review and after Compliance review. The maker may Withdraw to Draft, or the named reviewer/approver may Return for correction. Current review fields are cleared and the prior workflow remains in history. Edit the Draft and submit it again for fresh Compliance review and independent final approval. Approved source editions cannot be edited; use a new source edition for source changes or the separate approved-metadata correction flow for supported register fields.

Validation messages in dialogs

If a dialog submission fails, its error is shown at the top of the dialog and receives focus. Your entries stay in place so you can correct them and retry. A long dialog scrolls to the error. The message remains until the next attempt or a new dialog; it is not repeated in a toast behind the window. Success messages appear on the page after a successful dialog closes. If the session ends, the dialog closes and sign-in is shown.

For Add at least one source clause / para before submitting, cancel the review dialog, add clauses to the selected Draft edition, then submit again. The visibility fix does not remove this prerequisite.

One pending edition and Draft cancellation

Only one edition per instrument may be Draft, In review or Reviewed. While one is pending, Open pending edition replaces New version and a notice identifies the edition and required action. Complete approval, record a rejection, or cancel the Draft before creating another edition. Withdraw to Draft and Return for correction keep the pending slot occupied.

The maker with Author access can select Cancel draft and enter a reason of at least 10 characters. A Draft under review must first be withdrawn to Draft. Cancellation is permanent; the edition cannot be edited or submitted again. It remains in Source edition and Versions as Cancelled, with the reason, actor, date, source, clauses and prior workflow history retained. The approved effective edition stays unchanged. Use a different version number for a replacement edition.

Cancelling the initial Draft also closes the unapproved instrument as Withdrawn. Existing records are retained. If older data contains multiple pending editions, links identify them all; their makers must cancel extra Drafts before another submission can proceed. API checks enforce these rules even for stale browser tabs.

Add or edit master and organisation records

  1. As Admin, open Master data and choose a tab. In Other lookups, choose the lookup type and apply Search. Use Add for a new record or Edit beside an existing row.
  2. Enter its code, name and displayed attributes. A new code must be unique; existing codes are read-only. Reference dropdowns are searchable. New regulatory domains start as Draft only; assign the bank-approved owning department before enabling review submissions.
  3. Enter Reason for change, then save. A validation error stays in the dialog with your values. Cancel closes without saving. Inactive records remain retained for historical references.
  4. For organisations, open Organisation hierarchy, select a unit and choose Edit or Add child unit. Add child fills its parent; the page's Add organisation unit action starts a separate new unit. Select the type, parent and dates, record a reason and save. Parent options exclude the current unit and its descendants. A parent must be active and effective for a new link.
  5. Moving a unit recalculates descendant levels and changes the organisations included in descendant role scope. It does not move users' Home organisation, approve an LDAP department or change role assignments. Deactivate or move active children before deactivating their parent. The BANK root's structural settings stay protected.

Role display names can be edited; new permission roles and role code/activation changes require a deployment change. Regulators with retained non-Draft approval history cannot be overwritten by this editor. Master edits retain before/after audit evidence and the administrator's reason; this is not a business source approval.
